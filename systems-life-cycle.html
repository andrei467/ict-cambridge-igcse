The Systems Life Cycle

Every new computer system is built in stages. This page walks through the six stages — analysis, design, testing, implementation, documentation and evaluation — with a quick activity at the end of each one.

Stage 1 Analysis

The system life cycle is a structured process that guides the planning, creation, testing and deployment of an information system. It makes sure systems are systematically developed, meet the needs of stakeholders, minimise risks and maximise efficiency.

The first stage is analysis. Its purpose is to gather detailed requirements from stakeholders and analyse them to understand what the system should accomplish.

Research methods

Research methods are different ways a systems analyst could analyse the current IT system to understand its state and identify areas for improvement. There are four main methods:

  • Observation — watching users interact with the current system to see how it works
  • Questionnaires — a structured set of pre-determined questions to get the views of the workforce, clients and other system users
  • Interviews — one-to-one question and answer sessions that let the analyst dig deeper into the views of existing users
  • Looking at the existing system (including paperwork) — a full look at its state: training manuals, how paperwork is filed, operational instructions, accounts etc. Helps identify the scale of the problem, memory requirements and any input/output devices
Research methodAdvantagesDisadvantages
ObservationReliable data · Inexpensive · Good for an overall picture of the existing systemPeople don’t always behave the same way when observed
QuestionnairesQuick · Inexpensive · Can be anonymousCan’t ask follow-up questions · Low response rate · Answers might be vague
InterviewsCan monitor body language and facial cues · Employees can express opinions in a safe environment · Questions can change based on responsesTime consuming · Cannot remain anonymous · Employees may be uncomfortable and not give honest answers for fear of repercussions
Looking at existing systemObtains information that can’t be obtained from other methodsTime consuming, which can be costly

Analysing the current system

To fully analyse the current system, a number of key aspects must be identified:

AspectWhat it means
InputsData or information entered into the system
OutputsData or information generated by the system
ProcessingTasks performed by the system on the inputs to produce the outputs
ProblemsIssues that users face with the current system
User requirementsWhat users need from the new system
Information requirementsData or information the new system must process
  • Data flow diagrams (DFDs) help analysts understand the inputs, outputs and processing in the existing system
  • A requirements specification is drawn up from the results of the analysis — how the new system will work, how it will be deployed, and a time scale

Hardware and software selection

  • Identify suitable hardware — consider system requirements, compatibility and cost; justify choices based on user needs and system performance
  • Identify suitable software — consider functionality, compatibility and ease of use; justify choices based on user requirements and system efficiency

Stage 2 Design

The second stage is design. Its purpose is to develop architectural blueprints for the system, including database design, user interfaces and system interfaces.

File / data structures

File structures are considered during the design stage and consist of defining field names, field lengths, data types and primary keys. A file consists of records, and records are made up of fields. Each record is identified by its unique primary key field.

Data typeDescriptionExamples
AlphanumericStores a combination of characters (letters or text) and numeric dataUsernames, postcodes, product codes, phone numbers
CharacterA single letter/symbolA, B, C etc.
TextStores a combination of characters (letters, text, symbols, special characters etc.) and numeric dataThis_is_an_example
BooleanStores data in a Yes/No or True/False formatY or N
NumericStores numerical data: integers, decimals, currency, date/time100 · 1.50 · £2.99 · 18/05/2024 or 14:58

Validation routines

Validation routines are checks placed on data being entered to make sure it matches the design of the system. They prevent errors and maintain data integrity.

Validation routineDescriptionExample
Range checkEnsures the data entered as a number falls within a particular rangeFor children aged between 5 and 10, checks that numbers <5 and >10 are not accepted
Length checkChecks the length of a stringPassword must be a minimum of 8 characters, so checks the length is >=8
Type checkChecks the data type of a fieldEnter distance in whole miles, checks that decimals are not accepted
Format checkEnsures the data has been entered in the correct formatEnter date of birth (DD/MM/YY), checks the format is correct
Presence checkLooks to see if any data has been entered in a fieldEnter your username, checks the field has not been left blank
Check digitNumerical values that are the final digit of a larger codeBarcodes

Input & output formats

These are design considerations for how data is captured from users (input) and displayed to them (output).

Input formats — a data capture form collects data from a user in a structured format. It should aid collection by:

  • Having a user-friendly layout — short, visually appealing, logical flow
  • Providing clear instructions — concise, at the beginning
  • Using appropriate question types — multiple choice, drop downs, checkboxes etc.
  • Using validation routines

Output formats — showing the results of processing, on paper or on screen, should consider:

  • Screen layouts — how information is presented to users on a screen
  • Report layouts — how information is organised in a printed or digital report
  • Readability, visual appeal and efficient use of space

Stage 3 Testing

The third stage is testing. Its purpose is to verify that the system meets all requirements, functions correctly and is free of bugs, using various testing methods.

Test strategies

A test strategy is a method of testing a completed system to make sure all parts work as intended.

  • Systems are designed in a modular format
  • Each module needs to be tested independently
  • Testing is done again once all modules are joined together
  • The results may indicate changes need to be made — testing is repeated once all changes have been made

Test designs

Test designWhy?
Data structuresTest all data is stored correctly
File structuresTest all data is stored in the correct format
Input formatsTest that data can be entered correctly
Output formatsTests that screen output and reports are in the correct format
Validation routinesTests that the system rejects unreasonable data being inputted

Test plans

A test plan is designed and implemented to ensure thorough testing of a system. It includes:

  • Test data — specific data used for testing purposes
  • Expected outcomes — predicted results based on the test data
  • Actual outcomes — results obtained from testing
  • Remedial action — steps taken to fix identified issues

Test data

There are four main categories of test data used when performing final testing on a system:

TypeDescription
NormalData that should be accepted by the system; it has a known outcome
ExtremeData that is on the limits of what is acceptable
AbnormalData outside the limits of what is acceptable; it should be rejected by the system
LiveData from the old system used on the new system; it has known outcomes, so results can be compared to make sure the new system works

Stage 4 System implementation

The fourth stage is implementation. Its purpose is to deploy the system to the production environment and make sure all components work together in the live setting. It happens after a system has been fully tested and is working correctly.

Implementation happens in two stages: data is transferred from the old to the new system, then the system changeover takes place — moving from the old system to the new one. There are four ways to do a changeover:

  • Direct changeover — the old system is replaced by the new system immediately. Used when quick implementation is necessary
  • Parallel running — both old and new systems run simultaneously for a period before the old system is phased out. Used when a smooth transition with minimal risk is required
  • Pilot running — the new system is implemented in a small, controlled environment before full-scale implementation. Used when testing the new system in a real-world setting
  • Phased implementation — the new system is implemented in stages, with each stage replacing a part of the old system. Used when a gradual transition is preferred to minimise disruption
ImplementationAdvantagesDisadvantages
Direct changeoverFast implementation · Cost-effective as only one system is in operationHigh risk of failure · No fallback · Users can’t be trained on the new system · No backup of the system
Parallel runningLower risk · Easy comparison of systemsTime-consuming · Resource-intensive
Pilot runningLow risk as only trialled in one department/centre/branch · Allows for fine-tuning · Staff have time to train with the new system · Few errors as it’s fully testedSlower implementation · Potential inconsistencies · Confusion as there are 2 systems in use · No backup for the department/centre/branch using the new system
Phased implementationReduced risk · Easier to manageTakes longer · Potential compatibility issues

Stage 6 Evaluation

To evaluate a system you must assess the efficiency, the ease of use and the appropriateness of the solution. After a successful evaluation you will be able to identify limitations and propose improvements.

Efficiency of the solution

Evaluate the system’s performance in terms of resource usage, time and cost. Is it operating optimally, or could improvements be made? Identify areas consuming excessive resources or time, and suggest ways to optimise them.

Questions to ask: Does it operate quicker than the previous system? Does it reduce staff time in using the system? Does it reduce staff costs?

Ease of use

Examine how user-friendly and accessible the solution is for its intended audience. Is it easy to learn and use, and can users accomplish their tasks without difficulty? Describe the user interface and how it helps interaction, and mention any user feedback and the issues they encountered.

Questions to ask: Are all users able to use the system and make bookings easily? Can they change and cancel bookings easily? Can all staff understand how to use the system with minimal training?

Appropriateness of the solution

  • Compare the implemented solution with the original task requirements and evaluate how well it meets the intended purpose
  • Outline the initial objectives and discuss how the solution addresses each one; highlight any requirements not fully met and possible reasons why
  • Collect users’ responses to the results of testing — feedback can show potential issues and improvements, and help determine overall user satisfaction
  • Summarise the testing process, including test data, expected outcomes and actual outcomes

Questions to ask: Is the system suitable for each of the departments? Does it meet the needs of the customers? Does it meet the needs of the staff? Does the solution match the original requirements?

Identify limitations and propose improvements

Based on the analysis of efficiency, ease of use, appropriateness and user feedback you should now be able to list the limitations and explain each one, then recommend specific changes or enhancements that could address them and improve the system.
